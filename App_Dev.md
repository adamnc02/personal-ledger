### Session decisions & progress (2026-09-03)

**Decisions locked in this session (surfaced explicitly, per usual practice, rather than defaulted):**
- `BillLocation` is genuinely extended to a three-way `'personal' | 'joint' | 'pot'` — NOT an additive field layered on top of `'personal'`. A pot-located bill/loan carries `potId` alongside `location`, the same way a joint one carries `payee`/`payeeSharePercent`.
- A pot-paid bill/loan payment is **purely internal to the pot** — it does NOT touch personal cash when it fires. The real personal-cash-out event is the earlier deposit INTO the pot. This mirrors how `credit_card_spend` never touches the personal ledger.
- If a pot doesn't have enough balance to cover what's due from it, that's not something the app guards against — the Salary Sorter (next feature) is the intended mechanism for making sure the right amount lands in the pot after payday.
- A bill/loan's location change is **historized** exactly like every other effective-dated change in the app (`locationEffectiveFrom`/`locationHistory`, same shape as `amountEffectiveFrom`/`amountHistory`) — but unlike an amount change, it's NOT purely forward-looking: the chosen effective date retroactively rewrites every already-existing Transaction for that bill/loan dated on/after it, **including already-cleared ones**, so Personal's balance updates accordingly. Transactions dated before the effective date are left untouched.
- If a loan is tagged to a pot, that governs ONLY its regular monthly payment. A recurring overpayment has its **own, independent** location choice (personal or a pot — never joint), chosen via its own location-picker-first step, editable afterward like any other field (a flat overwrite, not historized — it's a standing arrangement's setting, not a fact about a specific past payment). A one-off lump overpayment or a full settlement is **never** pot-funded, regardless of the loan's own location.
- A JOINT loan's recurring overpayment always follows the loan (ignores any pot override on the overpayment itself) — deliberately, so a pot-funded (unsplittable) amount can never corrupt the joint payee-split math. Nobody's asked for "a joint loan's overpayment funded by one person's personal pot" as a real feature yet; if that's wanted later, it needs its own decision.
- Pot's own recurring-deposit/pause mechanics mirror `SavingsPot`'s exactly (monthly-only, flat multi-select pause list) — but `Pot` is a genuinely separate top-level entity from `SavingsPot`, not an extension of it (no interest, no goals; a Pot's bill/loan membership is derived from the owning bills/loans' own `potId`, not stored on the Pot).

**What this means for Salary Sorter (next session) — how a sort should land as transactions:**
Salary Sort's output is, structurally, just a batch of `transfer` transactions dated to a payday — the mechanism to create them already exists (`logTransfer`). What's still needed, proposed here as a concrete starting point rather than a locked decision:
- A new top-level `SalarySort` entity (one per configured payday occurrence — "each salary sort is specific to the salary, does not persist for future pay periods"), something like `{ id, payDate, targets: [{ to: TransferLocation, amount, transactionId }] }`. `personId` doesn't need its own field — the sort is always against the primary person's own salary, per this session's "current account is always me" decision, which also settles the earlier open question of whether Salary Sort should be available on anyone's pay pill: **only the primary person's**.

Likely needs: a new `sourceType: 'salary_sort'` added to `Transaction`'s `sourceType` union, `sourceId` pointing at the `SalarySort.id`, and each target storing back the `transactionId` it created (or resolving it by `sourceId` + `toLocation` at read time — either works, pick one and document it).

### Session decisions & progress (2026-09-04, continued — Salary Sorter data layer)

**Decisions locked in this session (surfaced explicitly, per usual practice):**
- The conflict guard is genuinely bidirectional but shares ONE exact-match rule (`locationsEqual` — same location type + id, no amount check) both ways: (a) sorting a salary when a scheduled one-off or already-active recurring transfer already exists for the same destination/date prompts **Go ahead** (create alongside) / **Skip** (drop just that target); (b) creating a NEW one-off or recurring transfer where an already-saved `SalarySort` already targets the same destination prompts the same **Go ahead** / **Cancel** (recurring: template isn't created at all) — scanned across this payday + the next 3 for a recurring template (resolved via `generateTransactionsForTemplate` against a draft template), a single date for a one-off. - `SalarySort.targets[].transactionId` points at a REAL, independently-editable `Transaction` (`sourceType: 'salary_sort'`) — not a synthetic/generated row, same as any other hand-logged transfer. `logTransfer` now returns the created id (previously `void`) so this link can be stored at creation time.
- Two-way edit sync (Transactions page ↔ the sort itself): editing a linked transaction's AMOUNT patches the matching target's amount; editing its DATE **detaches** it (the transaction survives as an ordinary transfer, sourceType/sourceId cleared, and its target drops off the `SalarySort`); deleting it drops just that target, leaving the rest of the sort intact. If a `SalarySort` is ever left with zero targets (every target detached/deleted/zeroed), the record itself is removed — an empty sort isn't a sort, and this is what the pay-pill's "coral when configured" check reads directly.
- Recurring transfers gain a genuine budgeting-cycle-follow mode, `followsCycleStart` (`RecurringTemplate`/`Transaction`), as a sibling to the existing `followsPayday` — resolved against `cycleBoundsForDate` the same way `followsPayday` resolves against `upcomingPaydays`. Mutually exclusive; `followsPayday` wins if both are somehow set. This is a general Transfer-pill capability, not salary-sort-only — a person whose budgeting cycle doesn't track payday (`PayCycleConfig.cycleStartFollowsPayday`) can now pick either for ANY recurring transfer.
- Which basis "this pay cycle" means for the sort's own suggestions — `[payday, next payday)` vs the person's actual configured cycle boundary — is a per-person, remembered choice: `PayCycleConfig.salarySortBasis: 'payday' | 'budget_cycle'`, undefined defaulting to `'payday'`. Lives on `PayCycleConfig` (not a new entity) since that's already the record edited from the Salary page's calendar-icon picker area, and already the "how does this person's cycle work" home.
- Suggestion prefill vs. label are deliberately DIFFERENT priorities, not the same rule read twice: the label always leads with "total due this window" when it's non-zero (so overriding one month doesn't stop the next month's label re-baselining against the real bill total), but the input box's own PREFILL uses the last-sorted amount whenever one exists for that destination, falling back to the due amount only when there's never been a prior sort to it. Savings pots have no bill/loan linkage at all, so their due amount is always 0 (label/prefill fall straight to last-sorted-or-nothing).
- Destinations are restricted to the primary person's OWN active pots/savings pots, plus the joint account if one exists — never a second person's own pot/savings pot.
- A target landing on 0 (typed over, or its own Clear button) is treated identically to omitting it entirely — "0 is null," per Adam's explicit call, so no zero-amount transfer transaction is ever created or left behind.

**A real quirk surfaced while writing the conflict-detection tests, worth flagging rather than silently working around:** `generateTransactionsForTemplate`'s `followsPayday` resolution (built in the Transfer session, unchanged by this one) walks the template's NOMINAL schedule first, then resolves each occurrence's date against `upcomingPaydays` — which only ever returns dates strictly AFTER the date it's given. Not fixed here — flagged for a real decision later, same as the `cycleStartFollowsPayday` gap.
